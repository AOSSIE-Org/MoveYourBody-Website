user-supplied input that reaches a server. The trust boundaries are (a) the
browser, which receives only build-time content, and (b) the CI/CD pipeline.

- Both `dangerouslySetInnerHTML` sinks are fed only build-time constants:
  `src/app/(root)/page.tsx:18` serialises the constant `"/en"` via
  `JSON.stringify`, and `src/app/[locale]/layout.tsx:109` serialises a JSON-LD

- No `searchParams`, `location` reads, `postMessage`, storage, `fetch` or `eval`
  in `src/`; all `href`/`src` values come from `src/config/links.ts` or
  hard-coded arrays; every `target="_blank"` link sets `rel="noopener noreferrer"`.
- `next/image` `remotePatterns` lists three fixed hosts, and `images.unoptimized`
  plus static export means no image optimiser runs (no SSRF surface).
- `src/app/api/info/route.ts` is `force-static` and emits fixed project metadata.
- No hardcoded secrets; `NEXT_PUBLIC_SITE_URL` holds a public URL only; `.env*`
  is gitignored.
- Workflows: `ci.yml` and `nextjs.yml` run on `pull_request` (no secrets for
  forks, read-only token), use `persist-credentials: false`, and the Pages
  `deploy` job (with `pages: write` / `id-token: write`) runs only on push to

## Notes

### Note 1: Unauthenticated machine-readable API surface — `src/app/api/info/route.ts:6`

- Category: design-tradeoff
- Observation: `GET /api/info` (exported statically, alongside
  `public/api/info.json`, `public/openapi.json` and
  `public/.well-known/ai-plugin.json`, which declares `"auth": { "type": "none" }`)
  serves project metadata with no authentication check, which the Next.js
  checklist item "missing authentication in an API route" would otherwise flag.
  The content is fixed public project information (name, licence, features,
  repository and store links) with no user data.
- Rationale: `AGENTS.md` ("Machine-readable files") documents these files as
  intentionally public descriptions of the project for crawlers and AI agents,
  and the site is a static export with no server-side auth layer. Adding
  authentication would contradict the stated purpose.

## Limitations

**Standing limitations**

- This review does not replace a full manual audit or a penetration test.
- This is static analysis of source text. Nothing was executed, fuzzed,
  or traced at runtime, so timing-dependent, load-dependent, or
  infrastructure-dependent issues cannot be confirmed here.
- Confidence scores are the reviewing model's own self-assessment, not a
  calibrated statistical probability.
- Absence of a reported finding does not mean the code is secure. Safety
  guardrails built into some models can cause a real vulnerability to be
  softened, generalized, or left out rather than reported in exploit-level
  detail, and training-data bias can make some vulnerability classes
  easier for a model to recognize than others. Treat this report as a
  floor on what a full audit would find, not a ceiling.
- Findings reflect the reviewing model's training data cutoff. A
  vulnerability tied to a very recently disclosed CVE or library advisory
  may not be recognized as such.

**Review-specific limitations**

- Third-party dependency and GitHub Action source code (`node_modules/`,
  `eps1lon/actions-label-merge-conflict`, `ossf/scorecard-action` and the
  `actions/*` steps) was out of scope and not reviewed.
- Repository and GitHub settings (branch protection, the `github-pages`
  environment's deployment-branch rules, Actions fork-PR approval settings)
  and GitHub Pages response headers are external state that could not be
  inspected; the deploy-path analysis assumes the workflow conditions shown in
  `nextjs.yml` are the only gate.
- Visual/animation components (`liquidMetalRenderer.ts`, mockups, sections)
  were checked by searching for injection, navigation, storage, messaging and
  network sinks rather than read line by line, since they handle no
  untrusted input.
